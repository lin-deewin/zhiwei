# Zhiwei V3 重构章程

状态：执行基线（2026-11-12）
目标分支：`refactor/v3`
基线分支：`main`
产品定位：Reading-Centric Personal Knowledge System

## 1. 产品使命

知微以个人阅读为入口，帮助用户收藏和管理外部资料、理解内容、记录自己的思考，并逐步形成可检索、可持续演进的个人知识体系。

核心路径：**收藏 → 阅读 → 理解 → 自主记录 → 知识沉淀 → 检索与回顾**。

## 2. 产品原则

1. 阅读优先：资料库是默认首页，阅读体验是最高优先级。
2. 来源与创作分离：知乎文章、回答等外部资料不等同于个人笔记。
3. 不强迫整理：收藏、阅读和批注不要求创建笔记或双向链接。
4. 标注各司其职：高亮表示重要，批注表达对选段的即时回应，笔记承载可独立发展的思考。
5. 链接有意义：双向链接主要用于个人笔记、知识卡片和主题页；外部文章之间默认不自动建立链接。
6. AI 可选：未配置模型时，阅读、同步、分类、关键词搜索和笔记管理仍可用。
7. 证据可追溯：AI 结果保留来源、正文版本和实际引用片段。
8. 数据安全：渐进式迁移；不覆盖用户修改，不丢失原始 Markdown、图片、标注、笔记及研究证据。
9. 简洁而非删减：通过信息架构隐藏低频复杂性，不以删除成熟能力换取表面简洁。
10. 模型和供应商无关：业务领域不得依赖单一模型服务。

## 3. 产品范围

### 核心工作区
- 资料库：文章/回答、收藏来源、分类、搜索、阅读状态、稍后阅读。
- 阅读器：正文、图片、目录、阅读位置、高亮、批注、文章来源。
- 个人笔记：自由笔记、读书笔记、知识卡片、主题知识页、笔记链接。
- AI 助手：单篇阅读辅助与跨资料检索问答。
- 研究工作区：研究问题、证据集、对话、研究成果及版本历史。
- 设置与同步：知乎账号、同步任务、资料目录、模型与索引设置。

### 非目标
- 不把系统变成强制 Zettelkasten 工作流。
- 不自动在外部文章之间创建双向链接。
- 不在本次重构中重写知乎抓取适配器。
- 不改变用户原始资料的存储位置和稳定 ID。
- 不为视觉效果引入不必要的前端框架或复杂基础设施。

## 4. 优先级

P0：数据安全、资料库首页、阅读体验、阅读进度、标注、个人笔记边界、核心导航。
P1：知识卡片、主题页、AI 助手整合、统一搜索、研究工作区体验。
P2：进阶知识图谱可视化、自动关联推荐、非核心体验优化。

## 5. 执行策略

采用 Strangler Pattern（渐进式替换）：
- 保留现有 API 和服务，先建立清晰的新页面与领域边界。
- 以适配层连接新旧模块，避免一次性大爆炸式改造。
- 每个迁移都有旧数据兼容测试、备份和回滚步骤。
- 页面迁移按用户价值逐步切换，不同时重写全部模块。
- 删除旧实现前，必须证明没有路由、API、测试或数据迁移依赖。

## 6. 当前代码基线（审计起点）

仓库已有 React 19、TypeScript、Vite、React Router 7；后端为 FastAPI/SQLite。主要前端集中在 `frontend/src/App.tsx`（约 65 KB），阅读工作区在 `ReaderWorkspace.tsx`，知识模块包括 `KnowledgeHub.tsx`、`KnowledgePage.tsx`，标签工作区在 `WorkspaceTabs.tsx`。后端阅读逻辑集中在 `backend/app/services/reading_workspace.py`，阅读 API 在 `reading_routes.py`，知识图谱服务在 `knowledge_graph.py`。

仓库已有设计/实施文档和若干测试，但 `AGENTS.md` 中关于“尚无自动化测试”的描述与当前测试目录不完全一致，必须以实际执行结果为准。现有文档中部分功能标记为已实现，不能替代运行验证。前端构建、后端测试、数据库迁移和真实知乎接入状态须在 E0 记录。

## 7. 完成定义

每个任务需具备：目标、范围、依赖、实现位置、数据影响、验收标准、测试证据、回滚方式。没有测试证据不得标记完成。每阶段交付变更摘要、测试结果、未解决问题和下一阶段入口。

## 8. 分支和发布

所有 V3 改造在 `refactor/v3` 进行；阶段性提交使用简短、明确的 conventional commit 风格。初期通过 Pull Request 对比 `main`，不直接改写默认分支。只有全部发布门槛通过并完成数据备份/回滚演练后才合并。
